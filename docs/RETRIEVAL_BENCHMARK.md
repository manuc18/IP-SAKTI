# IP-SAKTI — Phase 4 retrieval benchmark

**These are figures on an unverified benchmark.** 111 golden questions exist;
**none has been verified by a human**, and every record carries `verified: false`
as Phase 4 §1 requires. Nothing below should be read as a statement that IP-SAKTI
is accurate. It is a statement about where the expected chunk landed in a ranked
list, on questions whose ground truth was derived from the corpus itself.

Corpus version `0c94db57932c046d` · chunking version `2de178d2eda2ee11` ·
3,031 chunks · 22 logical documents · run 30 August 2026 · Python 3.14.3.

> **Sections 1–8 are the Phase 4 record and are unchanged.** They were measured
> on chunking **0.1.0** (3,031 chunks). Phase 5 repaired two classes of wrong
> citation locator, which rebuilt the corpus to 3,073 chunks, so **none of the
> numbers below is comparable with a Phase 5 number** — A–D were re-run rather
> than carried forward. The raw Phase 4 runs are preserved verbatim under
> `data/evaluation/results/phase4-chunking-0.1.0/`. See §9 for what changed, and
> `docs/RETRIEVAL_ROUTING.md` for the Phase 5 benchmark.

## 1. Dataset

`data/evaluation/golden_questions.jsonl` — 111 questions over all 22 logical
documents, none verified.

| | |
|---|---:|
| Questions | 111 |
| Human-verified | **0** |
| Documents covered | 22 / 22 |
| Conceptual queries (no citation given) | 93 |
| Identifier queries (the query names the provision) | 18 |
| Questions expecting non-citable evidence | 1 |
| Questions with more than one expected chunk | 2 |

The two query families are separated deliberately, because they measure
different things and mixing them hides both. An identifier query — *"What does
section 3(p) of the Patents Act exclude?"* — has already named its answer, and
answering it is a lookup. A conceptual query — *"Is the mere discovery of a new
form of a known substance patentable?"* — is the case retrieval actually has to
solve. A single headline number computed over both is dominated by whichever
family happens to be larger.

Coverage is uneven, and follows the corpus rather than any target: 18
biodiversity/ABS questions, 16 patents, 12 trademarks, 12 copyright, 11 GI, 11
plant varieties, 10 drug regulation, 9 designs, 9 TRIPS, 2 Ayurveda Aahara, 1
IPR policy.

## 2. Ground-truth methodology

Ground truth was not generated by asking a model what the answer is. Each
question was written against a provision, and states four things: the document,
the kind and number of the unit (`section 53`), and one or more **anchor
phrases** that must occur in the text of that unit. The chunk id was then
*resolved* from the corpus rather than transcribed, and a question whose anchors
did not occur was rejected and rewritten. Three were, during authoring.

That gives a ground truth which is checkable rather than asserted, and
`scripts/evaluation/validate_golden_dataset.py` re-checks it on demand:

* every expected chunk and document exists in the current corpus;
* every expected locator agrees with the chunk's own locator metadata — a
  question claiming `Section 22` cannot resolve to a chunk the pipeline labelled
  `Rule 22`;
* every anchor phrase still occurs in the expected text;
* a question requiring authoritative citation expects only citable chunks, and
  an unlocated chunk is expected only where the record says `allow_non_citable`.

```
questions            111
human-verified       0
documents covered    22 / 22
GOLDEN_DATASET: PASS  (0 failing checks)
```

**What that PASS does and does not mean.** It certifies that the references
resolve and the anchors hold. It does not certify that the provision named is
the *best* answer to the question, or the only one — that is a legal judgement,
and it is exactly what `verified` is reserved for. No automated step in this
repository can set `verified` to true; `benchmark_retrieval.py --verified-only`
currently evaluates zero questions and says so, which is the correct behaviour
and not a bug.

## 3. Retriever configurations

| | |
|---|---|
| **A · BM25** | Okapi, k₁ = 1.2, b = 0.75. Indexes `text` only. No stemming, no stopword list. 18,695 terms over 3,031 chunks, mean length 211 tokens. |
| **B · BGE-M3** | `BAAI/bge-m3`, revision `5617a9f6`, 1024-dim, L2-normalised, max_seq_length 1024, float32, batch 8, MPS. Cosine via dot product. |
| **C · BM25 + identifier boost** | A, plus a metadata bonus for chunks the query cites by name. Weight 1.0 × the query's own best BM25 score. |
| **D · Hybrid RRF** | A ⊕ B by Reciprocal Rank Fusion, k = 60, fusion depth 50, equal weights. |
| **D′ · Hybrid RRF (boosted)** | C ⊕ B, same fusion. Not one of the four asks; see §8. |

The tokenizer is legal-aware by necessity: `3(p)`, `31bis`, `15(7)`, `27.1`,
`117A`, `33EEB` and `PPV&FR` all survive as single tokens, and nothing is
stemmed. It also emits the leading number of a composite identifier alongside it,
so a query for `3(p)` can still match text that only ever writes "3.".

**Why the boost reads metadata, not text.** The string `3(p)` almost never
appears in the text of section 3 — the PDF sets out "3." as a heading and "(p)"
as a clause thirty lines below. The citation lives in the chunk's *locator*, so
that is where identifier matching looks. This is also why it is a scoring
component rather than a second engine: A and C are separate retrievers producing
separate results files, so the benchmark can say what the boost is worth instead
of assuming it earns its place.

Embeddings are cached under a fingerprint of every chunk id paired with a digest
of its text, so re-chunking invalidates the cache automatically and an unchanged
corpus never re-embeds. Storage is a 12 MB `.npy` matrix with a JSON sidecar. No
vector database was introduced: pgvector is not configured in this project, and
adding one to hold 3,031 vectors would be infrastructure work standing in for
progress. The `Retriever` interface is the one pgvector would satisfy later.

## 4. Metrics

Relevance is binary. **Recall@k is hit-rate**: a question counts as recalled when
at least one expected chunk is in the top k — the right question for a legal
answer engine, which must put the reader in front of the provision, not
enumerate every chunk it was split into. **nDCG@k** uses IDCG over the first
`min(|expected|, k)` positions, so a question with three expected chunks is not
penalised for the fact that only one can be rank 1; with a single expected chunk
it reduces to `1/log₂(rank+1)`. **MRR** takes the first expected chunk to appear
and contributes 0 beyond the evaluated depth, so it is depth-dependent — depth 10
throughout.

Document-level recall is reported alongside because it separates two very
different failures: retrieving the wrong statute, and retrieving the right
statute at the wrong provision. Only the first is a search failure.

BGE-M3 puts the correct **statute** in the top 5 for every question in the
benchmark. Its remaining failures are all about which provision within it.

### 5.2 By query family — where the averages come apart

| Retriever | Concept. R@1 | Concept. R@5 | Concept. MRR | Ident. R@1 | Ident. R@5 | Ident. MRR |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A · BM25 | 0.344 | 0.710 | 0.507 | 0.389 | 0.556 | 0.477 |
| B · BGE-M3 | **0.731** | **0.914** | **0.817** | 0.611 | 0.889 | 0.756 |
| C · BM25 + boost | 0.355 | 0.742 | 0.523 | **0.889** | **1.000** | **0.935** |
| D · Hybrid RRF | 0.581 | 0.882 | 0.713 | 0.556 | 0.778 | 0.630 |
| D′ · C + BGE-M3 | 0.591 | 0.882 | 0.723 | 0.833 | **1.000** | 0.898 |

This table is the main result of the phase, and it is invisible in §5.1.

**The identifier boost does precisely what it was built for and nothing else.**
On the 18 queries that cite a provision it takes Recall@1 from 0.389 to 0.889 and
Recall@5 to **1.000** — every cited provision, in the top five, every time. On
the 93 conceptual queries it moves Recall@1 by 0.011, which is one question. A
component that helps exactly where it claims to and is inert elsewhere is a
component worth keeping separable; had A and C been merged into one engine, this
would have shown up as a modest overall gain of unclear origin.

**Neither approach dominates.** BGE-M3 is far better at conceptual retrieval
(0.731 vs 0.355 Recall@1) and clearly *worse* at citation lookup (0.611 vs 0.889).
They fail on different queries, which is the precondition for fusion helping —
and yet.

### 5.3 Filtered variant (`--filters declared`)

Filters derived from the query text alone, applied only where the query names a
domain or jurisdiction:

| Retriever | Recall@1 | Recall@5 | Recall@10 | MRR |
| --- | ---: | ---: | ---: | ---: |
| A · BM25 | 0.351 | 0.703 | 0.820 | 0.501 |
| B · BGE-M3 | 0.703 | 0.892 | 0.937 | 0.791 |
| C · BM25 + boost | 0.432 | 0.766 | 0.865 | 0.577 |
| D · Hybrid RRF | 0.568 | 0.847 | 0.919 | 0.683 |

**Metadata filtering made retrieval slightly worse**, across every retriever.
The keyword map that infers a domain from query wording is the culprit: "How
does the Drugs and Cosmetics Rules define an Inspector?" matches `drug`, and
questions that span domains — a biological-resource question that is really about
patents — get pinned to one. Recall@10 falls furthest (0.964 → 0.937 for dense),
which is what excluding the right document looks like. The honest reading is that
a hand-written keyword classifier is not good enough to filter on, and the
unfiltered run is the one to quote.

### 5.4 Latency

Mean per query, 111 queries, M-series CPU/MPS: BM25 2.5 ms · BM25+boost 3.7 ms ·
BGE-M3 238 ms · Hybrid 221 ms. Dense latency is dominated by embedding the query;
the 3,031 × 1024 similarity scan is negligible. Nothing here is optimised, and
the figures are recorded so a later change can be seen rather than argued about.

## 6. Error analysis

Failures at Recall@5, classified by `scripts/evaluation/error_analysis.py`. A
failure is labelled only when a rule can point at evidence in the run; anything
else is reported as `unclassified` with its top-10 attached.

| Category | A · BM25 | B · Dense | C · Boost | D · Hybrid |
| --- | ---: | ---: | ---: | ---: |
| semantic mismatch | 23 | 8 | 20 | 10 |
| exact-term failure | 7 | 1 | 0 | 4 |
| document mismatch | 3 | 0 | 3 | 1 |
| chunking problem | 2 | 1 | 1 | 0 |
| **total failing Recall@5** | **35** | **10** | **24** | **15** |

### 6.1 BM25's characteristic failure is that legal text repeats itself

*"What does rule 13 of the Patents Rules require of a specification?"* returns
Form 13, Form 2, the Second Schedule, Rule 139 and Form 4 — every one of them a
document about forms and numbers in the Patents Rules, none of them Rule 13.
Term frequency cannot separate a provision from a form that mentions it. This is
the whole case for the identifier boost, and after it, Rule 13 is rank 1.

### 6.2 Dense retrieval's characteristic failure is the neighbouring provision

Eight of dense's ten failures are `semantic mismatch`: the right statute in the
top 5, the wrong provision. *"What is the minimum term of patent protection
under TRIPS?"* returns the TRIPS preamble and Article 66 (transition periods for
least-developed countries) ahead of Article 33 (term of protection) — plausibly
similar text, wrong answer. A reranker is the standard remedy; this is the
evidence for trying one.

### 6.3 Section 3 has a doppelgänger

For *"section 3(p) of the Patents Act"*, both C and B rank
`chapter-xxiii-schedule-section-3` — an entry in the Act's repeal Schedule that
also carries `section: 3` — at or above the real section 3. The identifier boost
cannot tell them apart, because on the metadata it reads they are identical. The
fix is at chunk level, not retriever level: schedule entries should not carry the
locator of the provision they amend.

### 6.4 Retrieval surfaces non-citable text, and says so

Across the 1,110 hits in each unfiltered run, 33–49 are chunks that cannot be
cited, and 5–8 of the 111 questions get a non-citable chunk at **rank 1**. This
is the invariant working, not failing: an unlocated chunk stays retrievable
because suppressing statutory text from search helps nobody, and it arrives
labelled `citable: false` so an answer layer can refuse to quote it. Every stored
result was checked against the chunk it came from; no retriever alters the flag.

### 6.5 Roughly 37% of retrieved evidence comes from a stale source

413–427 of every 1,110 hits are from documents Phase 3 found stale — the Drugs
and Cosmetics Rules to 2016, the Patents Rules to 2017, TRIPS in its 1994
unamended text. Retrieval is faithful to the corpus; the corpus is out of date in
places. `temporal_status` now rides on every chunk and every result, so this is
visible and filterable rather than silent.

## 7. Known limitations

**No question has been verified by a human.** Everything above is provisional.

**The benchmark was written by the same agent that built the retrievers.** The
questions were authored from provision headings, so they inherit that
vocabulary — which favours dense retrieval, and probably inflates §5.1 relative
to how a member of the public would phrase the same question. An independently
written question set is the single most valuable thing that could be added.

**CBD Articles 1–39 and Nagoya Articles 1–20 have unusable locators.** Phase 2's
treaty parser collapsed them into `preamble-0-cN` chunks bearing invented
"Paragraph 3" and "Paragraph 7" locators — 15 such chunks in the CBD and 10 in
Nagoya, **all of them marked citable**. The text is real: `preamble-0-c8` is CBD
Article 15(4). This is worse than an unlocated chunk, because the citability
invariant only protects against a *missing* locator, not a wrong one, and dense
retrieval ranks two of these first for a question about the CBD's depositary. No
golden question was anchored to them, so they do not distort the metrics — but
they are a live correctness problem in the corpus and should be fixed before any
answer layer is built on it.

**The Ayurveda Aahara Regulations are still absent** (Phase 3 §2). The two
questions in that domain are answered from the scanned recipe index, and one of
them expects non-citable evidence by design.

**Latency figures are indicative only** — single machine, warm model, no
concurrency.

**RRF is unweighted and untuned**, deliberately: k = 60 is the published
constant. A k fitted to these 111 questions would answer a much less useful
question.

## 8. Recommended next experiment

Three things follow from §5.2, in order of expected value.

**1. Route, do not blend.** Nothing here beats picking the right retriever per
query. Dense owns conceptual queries (0.731 Recall@1); the boost owns citation
lookups (0.889, and 1.000 at Recall@5). `parse_identifiers()` already decides
which is which, deterministically, from the query alone. A router built on it
would beat every row in §5.1: taking each family's best gives Recall@1 0.757
against dense's 0.712, Recall@5 0.928 against 0.910, MRR 0.836 against 0.807 —
and it is a dozen lines. Measure it as experiment E rather than assuming it.

**2. RRF is the wrong fusion here, and D′ shows why.** Fusing the *boosted*
lexical list instead of plain BM25 (D′) lifts Recall@10 to 0.982, the best figure
in the table, and restores identifier Recall@5 to 1.000. But **no fusion beats
dense alone at the top of the list** — D′ is 0.631 Recall@1 against dense's
0.712. Rank-only fusion throws away dense's confidence, and BM25's list is weak
enough that averaging in its ranks actively costs precision@1. Try score-aware
fusion with normalised scores, or weight the dense list.

**3. Then a reranker, and not before.** With D′ the correct chunk is in the top
10 for 98.2% of questions, and dense puts the correct document in the top 5 for
100%. That is exactly the setup a cross-encoder is for: the recall ceiling is
already high, and the loss is ordering within the right neighbourhood — which is
also the shape of every `semantic mismatch` in §6.2. Phase 4 was told not to
build one, and the numbers now say why it is the right next thing.

Two corpus fixes should land alongside: strip the false `section` locators from
Patents Act schedule entries (§6.3), and re-parse the CBD and Nagoya treaty
structure (§7). Both are chunking bugs that no retriever can compensate for.

## 9. Phase 5 addendum — what changed after this report

Everything in §§1–8 stands as the Phase 4 record. This section says which of its
findings were acted on, and it does not restate or revise a single Phase 4
figure.

### 9.1 Two limitations in §7 were defects, and are fixed

**CBD Articles 1–39 and Nagoya Articles 1–20** (§7, §6.5) had invented
"Paragraph N" locators and were marked citable. Root cause: the cleaning stage
strips a line containing nothing but a number close to the page's own folio, and
the CBD and Nagoya typeset every Article number on its own line under the word
"Article". `|4 − page 10| ≤ 10`, so the number was deleted as a folio and the
Article headings dissolved. Articles 40–42 survived only because their numbers
had drifted past the tolerance.

The fix reads the layout rather than guessing the number: a bare number directly
beneath a centred `Article` line is a heading number, not a folio. All 42 CBD
Articles and all 36 Nagoya Articles now carry correct locators, and **zero**
preamble chunks are citable (was 15 and 10). Where a number genuinely cannot be
read, the Article opens unnumbered and reaches Phase 3 as
`locator_unavailable` / `citable: false` rather than being folded into the
Article above it.

**Section 3's doppelgänger** (§6.3) — `chapter-xxiii-schedule-section-3`, a
repeal-Schedule entry carrying `section: 3` — is gone. Numbered entries inside a
Schedule, Form or Annexure now take an `item` locator and are cited through their
container ("Patents Act, 1970 — Schedule, item 3"). The real section 3 is the
only chunk in the corpus carrying `section: 3`.

Fixing that surfaced a third defect §6.3 had not seen: **615 chunks corpus-wide**
carried both a container and a provision locator, 436 of them in the Drugs and
Cosmetics Rules, where a line reading `Form 37.` inside rule 150E's running text
opened a Form that swallowed rules 150F–161. Numbering that resumes the
instrument's own sequence now ends the container. The count is 0.

### 9.2 The recommended next experiment was run, and it worked

§8 recommended routing over fusion and estimated an upper bound of ≈0.757
Recall@1. Experiment E reaches **0.766** on the repaired corpus — above the
estimate, because the corpus fix contributed as well.

| Retriever | Phase 5 Recall@1 | Phase 5 MRR |
| --- | ---: | ---: |
| B dense | 0.712 | 0.807 |
| E routed | **0.766** | **0.843** |

Full Phase 5 tables, the router's rules, its fallbacks and its failure modes are
in **`docs/RETRIEVAL_ROUTING.md`**. Re-running A–D on chunking 0.2.0 moved them
only slightly (bm25 0.351 → 0.342, dense unchanged at 0.712, bm25_boost 0.441 →
0.451), which is the expected size of effect from a corpus change that touched
locators far more than text.

### 9.3 A latency hazard in §5.4

`DenseRetriever` memoises query embeddings and the benchmark ladder shares one
dense instance across experiments, so any retriever measured *after* another
retriever that shares its encoder records cache hits rather than work. Phase 5
re-measures latency on fresh instances. The §5.4 figures were taken under the
same hazard and should be treated as indicative only, which §7 already says.

## Reproducing

```bash
.venv/bin/python scripts/evaluation/validate_golden_dataset.py
.venv/bin/python scripts/evaluation/benchmark_retrieval.py --retriever bm25
.venv/bin/python scripts/evaluation/benchmark_retrieval.py --retriever dense
.venv/bin/python scripts/evaluation/benchmark_retrieval.py --retriever hybrid
.venv/bin/python scripts/evaluation/benchmark_retrieval.py --retriever all
.venv/bin/python scripts/evaluation/benchmark_retrieval.py --retriever all --filters declared
.venv/bin/python scripts/evaluation/error_analysis.py --retriever all --at 5
.venv/bin/python -m pytest tests/ -q
```

Every results file records corpus version, chunking version, retriever
configuration, model revision and timestamp. The first dense run embeds 3,031
chunks (~11 minutes on MPS); every later run reads the cache.
